# 自动建立缺失索引的旧契约：补充核对

2026-10-05；用户指出“没有的应该会自动建立index，只是可能没数据”。本轮只读核对源码和已有配置，没有执行实际建库、改配置、改实现或再次重启。

用户记忆正确。升级前 f873a593 与当前旧 ES7 实现一致：`es_search_interface.py:593–618` 的 `_get_index_name` 对传入的每个索引调用 `_ensure_index`；`:184–340` 的 `_ensure_index` 检查不存在时使用完整 mapping 调用 `indices.create`。之后按原请求继续查询，空私库不会贡献命中；公库仍可贡献。`auto_update_mapping=False` 只限制已存在索引普通字段补齐，不禁止创建缺失索引。

运行 ES8 的区别有两项：

1. `es8_search_interface.py:116–120,136` 以 `ensure_index_on_init` 控制全部 `_ensure_index` 调用；当前实际服务配置引用的 runtime JSON 将其显式设为 false，因此建库和已有向量mapping检查均被跳过。
2. `:142–148` 的分组只对每组第一个索引 `_impl_for`，即使启用这个开关，同组其余索引也不能保证经过建库/校验。

第三项是已证明的在线容错缺陷：缺库 search 404从 `:853,888` 上抛，最终服务三次尝试后HTTP200错误哨兵，使公库结果也丢失。恢复自动建库和恢复子路容错必须同时核对，不能把“跳过404”当作自动建库契约已经完整替代。

现有隔离07d08源码默认 ensure=True，`_group_indexes` 已逐个绑定/校验，并保留 native HNSW `_ensure_index` 的缺库创建路径；真实只读验证只证明 ensure=False 时查询失败隔离，本轮没有实测真实创建。运行配置仍是 false，故隔离代码文件或单纯重启并不能自行恢复建库行为。

修复方向：在旧引擎保持每个准确物理索引名称和原CRUD请求，对缺失索引按ES8完整HNSW mapping创建；已有索引继续执行映射兼容守卫，`auto_update_mapping=False` 继续禁止自动put既有mapping。在线多路查询保留成功路命中并记录失败，维护/迁移完整性接口不统一吞错。先离线验证真实方法的建库调用、空库/公库合并、多索引次序与失败路径，再在明确已授权的合成索引做真实写验收；不擅建此次不存在的workflow私库或staging。当前“不改运行配置/不部署/不重启”的范围未解除，本轮不以恢复旧行为之名改线上开关。

对前份定位报告的解释补充：旧引擎的msearch确实保留失败子请求之外的命中，但其正常执行路径**先尝试建库**。因此旧端查询所谓“缺失测试私库”可能已产生创建副作用，不能仅凭HTTP返回3条断定旧端直接忽略404，也不能凭测试调用是/search便断定没有持久写。本轮未检查/删除旧端此类索引，避免扩大操作；后续复测应先记录存在性，只读测试使用既有数据或离线边界替换。
