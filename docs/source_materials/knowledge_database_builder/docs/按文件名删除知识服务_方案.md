# 按文件名删除知识 —— 服务方案

> ⚠️ 本文档是**设计与实测记录**，其中 §1.2/§1.3/§4 描述的 `confirm_token` + `expected_count`
> 双校验已于 2026-09-17 按用户要求去掉：`/delete_by_file` 入参与 `/preview_delete_by_file` 一致，
> 是否确认由前端控制。接口现状以 **`docs/知识库检索服务_线上API文档.md`** 为准。
> 其余内容（来源白名单、Dice 阈值、wildcard 限制等实测结论）仍然有效。


面向前端的「按来源文件批量下架知识」能力。三个接口：**列名称 → 预览命中 → 执行删除**。

## 0. 先看一眼真实数据（本方案的所有取舍都来自这里）

在 `payoneer_olive` 上实测（`del_flag=0`）：

| 指标 | 值 |
|---|---|
| 全库条数 | 13151 |
| **无 `from_file_name` 的条数** | **262** |
| 不同文件名（去重） | 1022 |
| 单文件最多条数 | 1337（`群聊总结知识_合并版_20260905`） |
| 超过 500 条的文件 | 1 个 |
| **一个名字是另一个子串的** | **61 个** |
| **文件名含 `(` `)` `|` `&` 等字符的** | **51 个** |

字段映射（已确认）：

```json
"ext_info": {"from_file_name": {"type": "text",
             "fields": {"keyword": {"type": "keyword", "ignore_above": 256}}}}
```

`text` + `.keyword` 双字段 ⇒ **精确和模糊两种模式都能原生支持，不用改 mapping**。

## 1. 三个接口

沿用现有风格：POST + pydantic model + `success/message` 响应体，放在
`knowledge_database_search_service/src/knowledge_database_search_es.py`。

### 1.1 `POST /list_file_names` —— 预先获取待删除名称集合

前端第一步：让用户从**真实存在的名字**里挑，从根上避免"文件名不对"。

```jsonc
// 请求
{
  "index_name": "payoneer_olive",
  "keyword": "TikTok",        // 可选，为空则列全部
  "size": 200,                // 默认 200，上限 1000
  "include_deleted": false    // 默认只统计 del_flag=0
}
// 响应
{
  "success": true,
  "values": [
    {"value": "印尼 TikTok Shop-印尼", "doc_count": 429,
     "type_count": {"qa": 429, "segment": 0}},
    {"value": "东南亚 TikTok Shop-东南亚", "doc_count": 102,
     "type_count": {"qa": 102, "segment": 0}}
  ],
  "total_count": 2,
  "message": "..."
}
```

实现：ES `terms` 聚合 + 子聚合 `data_type`，`keyword` 用
`wildcard` on `.keyword`（大小写不敏感）做筛选。

> 已有 `/get_value_collection` 能列字段值集合，但它**不带 data_type 拆分、也不支持关键词筛选**，
> 且返回的是裸值列表。新接口复用 `get_unique_values` 的思路，不改动老接口（它有别的调用方）。

### 1.2 `POST /preview_delete_by_file` —— 预览命中（必经步骤）

**这是本方案的安全核心：删除前必须先预览，前端拿到 `confirm_token` 才能调删除。**

```jsonc
// 请求
{
  "index_name": "payoneer_olive",
  "file_names": ["Text.docx"],     // 支持多个
  "match_mode": "exact",           // exact(默认) | fuzzy，严格二选一，无兜底
  "data_types": ["qa", "segment"], // 默认两者都删
  "audit_results": null,           // 可选，默认不限
  "sample_size": 10                // 返回几条样例供人工确认
}
// 响应
{
  "success": true,
  "total_count": 149,
  "by_file": [{"file_name": "Text.docx", "count": 149,
               "type_count": {"qa": 149, "segment": 0}}],
  "type_count": {"qa": 149, "segment": 0},
  "samples": [{"id": "...", "title": "...", "data_type": "qa",
               "from_file_name": "Text.docx", "audit_result": 2}],
  "warnings": ["..."],             // 见 §2
  "confirm_token": "sha256(index+归一化条件+total_count)[:16]",
  "message": "..."
}
```

### 1.3 `POST /delete_by_file` —— 执行删除

```jsonc
// 请求
{
  "index_name": "payoneer_olive",
  "file_names": ["Text.docx"],
  "match_mode": "exact",                  // 必须与 preview 一致，否则 token 对不上
  "data_types": ["qa", "segment"],
  "audit_results": null,
  "confirm_token": "a1b2c3d4e5f6a7b8",   // 必填，来自预览
  "expected_count": 149                   // 必填，来自预览
}                                          // 一律软删 del_flag=1，不提供 hard_delete
// 响应
{"success": true, "deleted_count": 149, "message": "...",
 "snapshot_path": "data/deleted_snapshots/payoneer_olive_20260916_143022.jsonl"}
```

## 2. 模糊模式：真实存在的误伤风险

实测 **61 个文件名是另一个的子串**。典型：

```
'Mercado Libre' (376条) ⊂ 'Brand Protection Program - Mercado Libre United States'  (38条)
                        ⊂ 'Mercado Libre-GC#23929 -94828992'                        (5条)
'Noon' (93条)  ⊂ 13 个更长的名字，如 'Free-Noon-99646294-GC# 24731' (13条)
'橄榄枝计划' (146条) ⊂ '97285496-BM橄榄枝计划' / 'jiaxinrui 橄榄枝计划' / '橄榄枝计划（TK跨境店）'
```

**用户想删「Noon」这一个文件，模糊模式会连带删掉 13 个客户群的知识。**

所以模糊模式必须做到：

1. **`match_mode: "fuzzy"` 时，预览响应里 `by_file` 必须逐个列出被命中的**完整文件名**及条数** ——
   前端把这个列表显示给用户确认，而不是只显示一个总数。
2. 命中文件数 > 1 时，`warnings` 里必须给出显式提示：
   `"模糊匹配命中 14 个不同文件名，共 106 条，请逐一确认"`。
3. **`match_mode` 默认 `exact`**；fuzzy 是独立模式，命中后按 §11 返回
   `matched_name` + `dice_score` 供用户确认，**不做"转 exact 再提交"这种降级**。

### 通配符转义

51 个文件名含 `(` `)` `|` `&` 等字符。模糊模式用 `wildcard` 查询时，
**必须转义 `*` `?` `\`**（其余字符在 wildcard 语法里无特殊含义，但要保证不被当成通配）：

```python
def _escape_wildcard(s: str) -> str:
    return s.replace("\\", "\\\\").replace("*", "\\*").replace("?", "\\?")
# fuzzy: {"wildcard": {"ext_info.from_file_name.keyword":
#          {"value": f"*{_escape_wildcard(name)}*", "case_insensitive": True}}}
```

> 不要用 `match` on `text` 字段做模糊 —— 中文分词会把「印尼 TikTok Shop-印尼」拆开，
> 导致搜「TikTok」命中一堆不相关的、以及**漏掉**分词边界不对的。`wildcard` on keyword 是子串语义，
> 与用户对"模糊"的直觉一致。

## 3. 精确模式的坑：`ignore_above: 256`

`.keyword` 有 `ignore_above: 256`，**超过 256 字符的文件名不会被索引成 keyword**，
`term` 查询永远查不到它，且**不报错**——正是"静默查不到"这类问题的典型形态。

实测当前最长文件名未超限，但这是**将来会踩的雷**（长 URL 作为来源名时）。

处理：`preview` 阶段对每个 `file_name` 检查长度，
`len(name) > 256` 时进 `warnings` 并在该文件上标注 `"count": null, "reason": "文件名超长，keyword 未索引"`，
**不允许**它进入删除（否则用户以为删了，其实一条没删）。

## 4. 安全机制（为什么要 token + expected_count）

删除是不可逆的破坏性操作，且**并发下数据会变**。防线：

| 机制 | 防的是什么 |
|---|---|
| **必须先 preview 拿 token** | 防止前端跳过确认直接删 |
| **token = hash(index + 归一化条件 + total_count)** | 条件被改动过 token 就对不上 |
| **`expected_count` 与实际再次比对** | preview 之后有新数据写入 → 实际数 ≠ 预期数 → **拒绝执行**，要求重新预览 |
| **删除前写快照** | 可回滚，格式沿用现有 jsonl 快照习惯 |
| **默认软删 `del_flag=1`** | 与现有清理流程一致，可恢复 |

**不提供 `hard_delete`**（已确认不做），一律软删 `del_flag=1`，可用快照回滚。

### 关于 `audit_result`

默认**不限**（全删）。但要注意此前定的口径：`audit_result` 0/1 代表已有人审过。
如果前端场景是"删掉某份来源文件的全部知识"，不限是对的；
如果是"清理未审核的脏数据"，前端应显式传 `audit_results: [-1]`。
**接口不替业务做这个决定**，但 preview 的 `by_file` 里会拆分 audit 分布供判断。

## 5. 必须解决的工程问题

### 5.1 ES 分片静默取消（已知问题，直接影响本功能）

本仓已定位：阿里云 serverless ES 在**大结果集**请求下会取消部分分片却仍返回 200，
`hits` 不全而 `hits.total` 照报全量（详见 `function_schema/es_search_interface.search_multi_by_page.md`）。

对本功能的具体危害：

- **preview 的 `total_count` 可能偏小** → 用户以为只有 3 条，实际 300 条
- 更糟：**`expected_count` 校验会因此误判**，把正常删除拦掉，或放行一个不完整的删除

处理：

1. 计数**一律用 `_count` API 或 `terms` 聚合**，不要用 `search` 取 hits 再 `len()` ——
   聚合/count 不受 `size` 截断影响，稳定得多。
2. 复用本仓已写好的 `_search_with_shard_check`（检查 `_shards.failed` + 重试 + 拆批）。
   **该修复目前未提交，本功能依赖它，应一并落地。**
3. 删除执行用 `update_by_query`（服务端批处理），不要"先查ID再逐条删"——
   后者正是会被截断的用法。

### 5.2 大文件分批

最大单文件 1337 条。`update_by_query` 本身能处理，但要：
- 带 `conflicts: "proceed"`（并发写入时不中断）
- 设 `requests_per_second` 限流，避免打满集群（本集群已被证实对负载敏感）
- 返回 `updated` / `version_conflicts` 供前端展示

### 5.3 那 262 条没有 `from_file_name` 的数据

本功能**够不着它们**。preview 响应里应带一句说明，避免用户以为"按文件删一遍就清干净了"。

## 7. 测试计划

按团队规则，优先 pytest 单测（mock ES），真实环境做集成验证。

**单测**（不碰真实 ES）：
- 精确 / 模糊两种模式生成的 ES 查询体正确
- **无兜底**：`exact` 查不到时返回 0，**不得**出现 wildcard/match 子句（即没偷偷转模糊）
- **无兜底**：`fuzzy` 最高 Dice < 0.9 时返回"未找到"，**不得**退回精确 term 查询
- **默认值**：不传 `match_mode` 时按 `exact` 处理
- **wildcard 转义**：文件名含 `*` `?` `(` `)` 时查询体被正确转义
- **子串误伤**：fuzzy 命中多文件时 `by_file` 列全、`warnings` 有提示
- **token 校验**：条件变了 token 失效；`expected_count` 不符则拒绝执行
- **超长文件名**（>256）被标记且不进入删除
- `data_types` 过滤：只删 qa / 只删 segment / 两者
- 分片失败时**抛错而非静默返回 0 条**
- **来源白名单**：每个查询体都含 `{"terms": {"from_type_norm": ["document","html","manual"]}}`；
  用白名单而非 `must_not: auto_learning`（否则中文旧写法 `自动学习` 会漏网）
- **Dice 判定**：`P-Chewy-...-Li&Zhao` vs `...-Li&Zhao D` 这类 0.97 的近似名，
  在 fuzzy 下取最大且 >=0.9 —— 用例锁住"取最大的那一个"的行为

**集成验证**（真实索引，用一个自造的临时文件名，删完即回滚）：
- 造 N 条测试数据 → preview 计数与实际一致 → 删除 → 校验 `del_flag` → 用快照回滚

## 9.1 只作用于非对话来源（`from_type_norm`）

**本服务只处理 `from_type_norm in ["document", "html", "manual"]`**，
即"来源于文件/网页/免审录入"的知识。对话来源（`auto_learning`）不在范围内。

理由：按文件名删除本就是"这份文档/网页不要了"的语义；对话学来的知识没有真正的来源文件，
它的 `from_file_name` 是群名/会话名，按文件名批量删会误伤。

### 实现：作为**强制基础过滤**，不是可选参数

三个接口的每一次 ES 查询（列名、计数、预览、删除）都必须带上：

```python
FROM_TYPE_SCOPE = ["document", "html", "manual"]
base_must = [
    {"term": {"del_flag": 0}},
    {"terms": {"from_type_norm": FROM_TYPE_SCOPE}},
]
```

**不要做成请求参数**——前端漏传或传错就会把对话知识删掉。写死在服务端，
需要调整时改配置常量。

### ⚠️ `from_type_norm` 有中文历史写法

实测 `payoneer_olive`（`del_flag=0`）分布：

```
document       8080        ← 在范围内
auto_learning  4093        ← 对话来源，排除
html            337        ← 在范围内
自动学习          334        ← 对话来源的中文旧写法，同样排除
teacher_training 258
other            43
manual            6        ← 在范围内
```

**`自动学习` 是 `auto_learning` 的历史中文写法**（本仓 MEMORY 有记录：
存量曾有 `auto_learning` 和 `自动学习` 两种写法并存）。
用**白名单**（`terms` 只放 document/html/manual）天然把它排除；
**绝不要用黑名单**（`must_not: auto_learning`）——那样 334 条中文写法的会漏网被删掉。

字段是**顶层 keyword**（不是 `ext_info` 下），可直接 `terms` 查询：

```json
"from_type_norm": {"type": "keyword"}
```

`index_name` 在三个接口里都是**必填参数**，由调用方显式指定操作哪个索引，服务端不设默认值。

## 11. 匹配模式：`match_mode` 严格二选一

**`match_mode` 说什么就是什么，没有兜底、没有自动降级。** 默认 `exact`。

| `match_mode` | 行为 |
|---|---|
| `exact`（默认） | 只用 `.keyword` 做 `term` 精确匹配。查不到就是查不到，**不会**自动转模糊 |
| `fuzzy` | 只走模糊召回 + Dice 判定。**不会**先试精确 |

```python
if match_mode == "exact":
    q = {"term": {"ext_info.from_file_name.keyword": name}}
    # 查不到 → count=0，preview 如实返回 0 并在 warnings 说明"精确匹配无结果"
else:  # fuzzy
    cands = fuzzy_candidates(index, name)
    best  = max(((dice(name, k), k, c) for k, c in cands), default=(0, None, 0))
    matched = best[1] if best[0] >= 0.9 else None
    # 达不到 0.9 → 视为没找到，不退回精确、不放宽阈值
```

### 模糊模式：Dice >= 0.9 且取最大的那个

```python
def _bigrams(s: str) -> set:
    s = (s or "").strip().lower()
    return set(s[i:i+2] for i in range(len(s) - 1)) or {s}

def dice(a: str, b: str) -> float:
    A, B = _bigrams(a), _bigrams(b)
    return 2 * len(A & B) / (len(A) + len(B)) if A and B else 0.0
```

模糊命中后，preview 必须返回 `matched_name`（实际会删的完整文件名）、`doc_count`、`dice_score`，
由用户确认。**这是展示确认，不是降级**——用户确认的就是模糊匹配到的那个名字。

### 实测：限定非对话来源后，两种模式都是 100%

对范围内（`from_type_norm in [document, html, manual]`）全部 **214 个真实文件名**逐个验证：

| 模式 | 定位到自己 | 误伤 | 未达阈值 |
|---|---|---|---|
| 纯模糊（Dice>=0.9 取最大） | **214/214 (100%)** | **0** | 0 |
| 精确 | 214/214 (100%) | 0 | 0 |

对照：**不限定来源**时（全库 1022 个文件名）纯模糊只有 47.8%，且有 **12 例误伤**。
那 12 例全是客户群文件名（`P-Chewy-GC#22398-93165827-Li&Zhao` 与
`...-Li&Zhao D` 这类只差一个尾缀，Dice 0.97 分不开）——**都是对话来源，
被 §9.1 的 `from_type_norm` 白名单挡在外面了**。

⇒ 限定来源之后，模糊模式本身已经足够安全，**不需要"精确优先"这种兜底**。

### ⚠️ `index.max_wildcard_length = 50`（实测发现，必须处理）

本索引该设置为 **50**，而线上有文件名长度超过 48（全库最长 158）。
直接拿全名做 `*{name}*` 会 **400 报错**：

```
RequestError(400, 'The length of wildcard [57] ... exceeded the allowed maximum of [50]')
```

处理：wildcard 只用名字的**前 48 字符**作为片段召回，再靠 Dice 做判定：

```python
should = [
    {"wildcard": {"ext_info.from_file_name.keyword":
                  {"value": f"*{_escape_wildcard(name)[:48]}*", "case_insensitive": True}}},
    {"match": {"ext_info.from_file_name": {"query": name}}},   # 补 wildcard 截断可能漏的
]
```

这两个 `should` 是**模糊模式内部的召回手段**（把候选捞全），不是"模式兜底"——
最终判定一律由 Dice >= 0.9 决定。
