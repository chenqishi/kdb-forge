## 8. 追查根因（用户追问后补充，2026-09-23）

### QA 质检遗漏已定位到模型调用前的本地去重

前文“质检阶段遗漏”是阶段定位，现在进一步确认：不是本样本模型漏返回，也不是运行异常，而是 `quality_tools/qa_quality_tools.py:deduplicate_qa_list` 在送模型前调用 `is_simlity_qa_info`，只要问题字符集合相似度 >0.9，**或答案字符集合相似度 >0.8**，就删除后来的条目。`commons.common_utils.context_dice` 实际比较字符集合的交并比，丢掉顺序与字符重复次数，日期文本特别容易误判。调用方虽然传入 title_threshold=0.95 / answer_threshold=0.9，函数内部却硬编码 0.9 / 0.8，形参没有生效。

生产 `qa_generation.log` 第 13097 行直接记录 `before dedup_len 36 afterlen 25`。离线只执行原有纯去重函数，36→25 完整复现，保留的问题集合与实际质量输出完全一致；没有调用模型或修改库。

具体误杀：Holiday Deals 的“12 月4 日（周五）12 月10 日（周四）”，被当作 Smart Savers 的“10 月16 日（周五）10 月22 日（周四）”的重复，答案字符相似度 0.846 > 0.8，而问题相似度只有 0.541。5 Days of Deals 则被当作 C12 日期问答重复。10 个活动问答在这一前置规则中消失，不是审核平台删除。

[复现证据](../output/codex_takeover_20260923/calendar_dedup_root_cause.json)。本轮读取的生产 quality_tools、common_utils、ES insert、ID 生成代码 SHA-256 与本地相同。未修改公共去重逻辑；该规则跨文档使用，修复需有行为回归验证。

### 44 条旧标记来自同 ID 的部分更新

`gen_data_id` 只由 title、content、data_type 计算 MD5，不包括 task_id 或版本号。因此新任务重新生成完全相同的问答时，新旧 ID 相同。底层名为 insert 的方法实际调用 ES `update`，body 为 `doc=data, doc_as_upsert=True`：已有 ID 就部分更新，没有 ID 才新建。

实际时间顺序：旧记录存在 → 旧记录被打 flag → 新任务生成相同问答/相同 ID → 更新旧记录的 task_id、audit_result 等字段，但新 payload 不含 ext_info.flag → 原旧 flag 留下。不是当时给尚不存在的新记录打了标记，而是原记录后来被新任务复用了。

全量比对 44 条的新插入 payload，**44 条均没有旧 flag**；不完整的打标前快照能找到其中 43 个同 ID（快照本来少于打标总量，不把剩余 1 条说成已获快照证实）。样本 ID `04e92b47304219ce218e82bf24dfc7f5`：旧快照为 audit=2、文件“补发配件资格.docx”；新 payload 为同问答、新 task_id、audit=-1，不含 flag；现记录同时保留新 task_id 和旧 flag。说明“先插新、后删旧”没有实现版本之间的 ID 隔离，且原审核状态也会被新 payload 覆盖。

[44 条前快照/新 payload/当前记录对照](../output/codex_takeover_20260923/old_flag_upsert_root_cause.json)。关闭 check_duplicate 只关闭相似知识检索去重，不改变同 ID upsert 行为，无法防止这一重叠。

### 源文件和映射问题的归因边界

源 DOCX 断尾发生在本轮上传、解析和生成之前（本地文件与生产下载文件哈希相同，断尾直接存在于 Word XML）。尚未取得这些 DOCX 的更上游导出/制作日志，因此不能确定是网站导出、转换脚本还是其他制作环节截断。
