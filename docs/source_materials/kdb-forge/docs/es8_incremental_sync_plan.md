## 实施顺序

1. **冻结绑定。** 使用已确认的 86 索引清单，显式绑定 provider 与当前原名目标；预检目标存在，禁止沿用 staging 名或自动创建目标。与正在执行的向量修复按索引互斥。
2. **独立采集增量。** 后台任务按受控周期运行，检索请求不触发旧 ES 同步。完整可靠的 CDC 必须接入覆盖**所有写来源**的持久变更日志，记录递增序号、索引、ID、操作和可恢复数据；物理删除必须有 tombstone，软删除也必须产生事件。
3. **先落地，再导入。** 将一个封闭日志区间写入本地 gzip NDJSON，持久化文件、SHA、条数及 manifest，再允许导入。导入程序只读取这些已完成的本地批次，不访问旧 ES。新增/更新保留 ID、业务字段及四类向量，不把过滤掉向量的 `_source` 当作完整备份。
4. **分开推进两个水位。** `exported_cursor` 表示已完整落盘；`applied_cursor` 表示目标已全部确认。按日志分区维护游标；只有该区间全部操作 ACK、计数/ID/内容及向量校验通过，才能原子推进 `applied_cursor`。删除重试保持幂等，旧事件不得覆盖新事件或复活已删文档。
5. **失败从本地重试。** 保留不可变批次及失败项，失败区间不越过、不靠跳过错误推进已应用水位；恢复时复用本地文件，不重新全量读取旧 ES。记录待处理数量、最近成功时间和失败原因。

## 历史补差与完成条件

无可靠日志时，时间轮询只能作为有缺口的过渡：先确认时区，采用固定上界、重叠窗口及可靠分页；超过 500 条不得截断后推进。它不能替代删除日志，也无法证明已捕获不更新时间的修改。

**过去未记录时标或日志的变更，不能仅凭新时间游标补齐。** 切换前必须对明确范围做受控对账、落盘补差并验证；需要整体扫描旧 ES 时，仍遵守用户的夜间启动及明确命令约束，不能为声称“最新”擅自重跑全量。

完成确认需同时具备：历史差异闭合、所有写来源纳入变更日志、86 索引消费到明确且已验证的来源截止游标、失败项为零。向量修复完成或历史批次成功，均不等于当前数据已最新。
