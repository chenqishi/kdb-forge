## 1. 核心风险：按文件名覆盖会造成同一篇文档两套知识

如果只按文件名匹配就执行，那 160 篇会被当作**新文件插入**，与库里的旧版本并存：

```
库里: 基础运营_管理我的团队页面.docx    63 条（旧版本，audit=2，线上在用）
新增: 管理"我的团队 (My Team)"页面.docx  N 条（新版本）
        ↓
同一篇文档两套知识同时可召回，新旧内容混着出
```

**这比不更新更糟** —— 不更新只是知识过时，重复会让 LLM 拿到互相矛盾的两份答案。

## 2. 方案

### 阶段一：建对照表（只读，必须先做且人工过目）

三级匹配，产出 391 行对照表：

| 级别 | 方法 | 预计覆盖 |
|---|---|---|
| L1 | 文件名精确匹配 | 231 |
| L2 | 剥掉库内 `分类_` 前缀后匹配 | 待测 |
| L3 | **正文内容比对**（解析新 docx ↔ 库内 segment 正文，字符 n-gram 相似度） | 兜底 |

每行输出：`新文件 → 库内旧文件名 / 无对应`，附匹配级别与相似度。

**L3 是关键**，因为它不依赖任何命名约定。判定阈值要保守（宁可判"无对应"让人工看，不可误判成另一篇）。

产出后**人工确认**，特别是：
- L3 匹配的（机器判的，要抽验）
- 判为"无对应"的（可能是真新文档，走新增流程而非更新）
- 那 4 组同标题的 `(2)` 文件

### 阶段二：确认生成侧无截断风险

⚠️ **已知隐患**：2026-09-19 查 mercado 时实测，一份 422 页的 PDF **QA 生成在第 123 页后整体断流**，23/32 个 segment 零产出。同一份文档另一次任务却跑完了（545 条），说明是**单次任务中断**而非规模硬限制，但触发条件未知。

执行前必须：
1. 统计这 391 个 docx 的页数/字数分布
2. 对最大的几个先试跑，验证 QA 覆盖到末页
3. 生成后**逐文件校验** QA 的 `from_page` 最大值 vs segment 的 `end_page` 最大值，缺口大的重跑

否则可能重蹈覆辙：跑完看着"成功"，实际只生成了前半部分。

### 阶段三：先插后删（按用户要求）

顺序固定为 **插入新知识 → 验证 → 软删旧知识**：

- 中间态是"新旧并存"（召回可能重复，但不会缺）
- 反过来会有"知识真空期"，线上问答直接答不出来

旧知识一律**软删** `del_flag=1`，不物理删，保留回滚。

### 阶段四：验证

1. **条数对账**：每个文件新旧条数对比，异常的单独看
2. **无残留**：旧文件名下 `del_flag=0` 应为 0
3. **无重复**：用新知识的标题去检索，确认不会同时召回新旧两版
4. **抽样检索**：挑 10~20 个典型 query，确认召回的是新版本

## 2.5 ★ 怎么更新：三种路径对比

对照表只解决"新旧对应"，不解决"怎么换"。实测发现**入库管线自带覆盖能力**，所以有三条路：

### 路径 A：走正常任务 + 管线自动覆盖（推荐）

`insert_data` 在 `check_duplicate=true` + `is_update_data=true` 时会自动查重并覆盖：

```python
duplicates = self.find_duplicates(data, ...)      # 向量检索找相似的旧知识
if duplicates and is_update_data:
    self.engine.update_value(update_value_dict={
        'del_flag': 1,
        'del_reason': f'cover_by_new {new_id}'},  # ← 留了溯源标记
        conditions=[{'_id': duplicates_ids}])
```

`config_for_search_index.json` 里 `check_duplicate: true`，即**默认开启**。

意味着：提交任务 → 新知识入库 → 管线自动软删被覆盖的旧知识，天然就是"先插后删"。

⚠️ **但实测 `wayfair` 里带 `del_reason` 的是 0 条** —— 这个机制在该索引上**从未实际触发过**，
不能假定它一定按预期工作。**必须先用 1~2 个文件试跑验证**：
- 新知识入库后，对应旧知识是否变成 `del_flag=1` + `del_reason=cover_by_new`
- 覆盖的是不是**同一篇**的旧知识（查重走向量相似度，可能误伤邻近文档）

风险点：查重是按**知识条目级**的语义相似度，不是按文件。可能出现
①同文件内新旧条目对不上 ②误删了别的文档的相似条目 ③改写较大的条目没被识别为重复→残留。

### 路径 B：任务生成 + 我按文件名精确软删（可控）

提交任务时**关掉自动查重**（`check_duplicate=false`），生成完后我按对照表
逐文件精确软删旧知识（`ext_info.from_file_name = 旧文件名`）。

- 优点：删哪些、删多少完全可控可预测，不依赖语义查重
- 缺点：多一步人工操作；中间态新旧并存（但这正是"先插后删"要的）

### 路径 C：原地改写（不推荐）

直接改旧条目的 title/content/向量。**不建议**：新旧条目数不一样（切分会变），
改不出来；且丢失版本痕迹，无法回滚。

### 建议

**小批试跑用 A，验证覆盖是否精准；若不可靠则全量走 B。**
无论哪条，都要留快照 + 按文件对账。

### ① audit 状态 —— **已定：跑完提前审核**（2026-09-21 用户确认）

新知识生成后**先走一轮提前审核**再替换旧的，避免"旧的删了新的召不回"的真空。
实施上即：生成 → 审核置为可召回状态 → 再软删旧知识。

原分析保留如下：

#### （原）audit 状态（影响是否白干）

新生成的知识默认 `audit_result=-1`（待审），**线上检索按 `audit_result in [1,2]` 过滤，召不回**。
而被替换的旧知识里 3863 条是 `audit=2`。

如果直接替换，结果是：**旧的（能召回）被删 → 新的（召不回）顶上 → 这 26% 的知识线上全部消失**。

参考：mercado 那边实测 9854/13405（73%）的 QA 卡在 `audit=-1`，审核积压是常态。

所以必须先定：
- **A.** 新知识沿用旧的 `audit=2`（立即可用，但跳过了人工审核）
- **B.** 走正常审核流程（安全，但这批知识会有一段时间召不回）
- **C.** 分批：先替换一小批走完审核验证流程，再推全量
