# Bol 公开材料覆盖天花板实测（payoneer_olive 补库试点）

日期：2026-08-29
任务来源：`/root/sell_agents/docs/payoneer_olive_kb_gap_tasks_20260829.md`（payoneer-olive session）
范围：**只做 Bol 一个平台的试点，只测不灌库**

## 一、结论先行

**Bol 的 51 条 P 类（公开知识库类）缺口，公开材料实测覆盖 34%~60%，取决于口径。**
目标是 41 条（80%），**无论用哪个口径都未达标**。

| 口径 | 覆盖 | 说明 |
|---|---:|---|
| **高置信**（两轮判定一致为 covered/partial） | **17/50 = 34%** | 最可信，用于下结论 |
| 并集（任一轮判有） | 30/50 = 60% | 上界，含 13 条不稳定判定 |
| 单次 top_k=8 | 25/50 = 50% | 不可单独使用 |
| 单次 top_k=20 | 23/50 = 46% | 不可单独使用 |

**两个口径差 13 条，全部是两轮判定不一致的条目。** payoneer-olive 独立实测发现
（相同候选、temperature=0 跑 3 次）：**判定不稳定的条目与人工识别出的误判高度重合** ——
即"飘"本身就是"判错"的信号。因此**高置信口径 34% 才是应该拿去做决策的数**，
60% 是乐观上界。

另外两点必须一起读：

1. 并集口径下未覆盖的 20 条里，**14 条至少有一轮被判为"渠道内部口径"**（Payoneer 专属流程，平台官网天然不会写）；
2. 因此即便按乐观的并集口径，**公开材料在 Bol 上继续加爬的边际空间也很小**——
   剩余可争取的主要是那 6 条非渠道内部项。

## 二、最重要的发现：卡住覆盖率的不是材料，是测量工具

三轮同口径对比（同一批 50 条 query）：

| 轮次 | 材料 | 切块方式 | 覆盖 |
|---|---|---|---:|
| r1 | 102 页 / 32 万字符 | 900 字符盲切 | 7/50 = **14%** |
| r2 | 639 页 / 190 万字符 | 900 字符盲切 | 11/50 = **22%** |
| r3 | 639 页 / 190 万字符 | **按 HTML 小节切** | 25/50 = **50%** |

**材料翻 6 倍只带来 +8pp；修一个切块 bug 带来 +28pp。**

### 切块为什么是决定性的

`selling-via-bol-as-an-eu-partner` 页里回答「一次没成功可以补资料吗」的关键句是：

> "If you don't hear anything within 5 working days? Then we will not proceed this time.
> **You are always welcome to try again next year.**"

900 字符盲切把它并进了一个**以营销话术开头**的块
（"Personal collaboration: direct contact with colleagues with local market knowledge..."）。
于是该块的向量代表的是**开头那段营销文案**，不是块里的答案：

- 目标块与该 query 的余弦相似度：**0.4451**
- 排名：**680 / 2492**

粗召回取 top-8，**永远够不到**。改成按 `<h1>~<h4>` 切之后，同一段答案成为一个
391 字符的独立块，标题 `... / Want to become a partner?` —— 标题即主题。

**通用规则：切块边界决定块向量代表什么语义。主题混杂的块等于没有向量。**

### 交叉验证：同类错误在对方项目上也存在

payoneer-olive 按同样方法自查，发现 `catfilter_eval_v4.KEEP_DETAIL=12`
（只送分数最高的 12 条候选给 judge，而平均召回 77.4 条）——
**每条缺口都是在只看 12/77 候选的情况下判的**。抽 60 条重判翻正 16.7%，
推全量约 58/348 是假缺口。

**两个错误同构，且都不会自己暴露**：下游 judge 的"判否"理由看起来完全合理，
它确实只看到了无关知识，错的是喂给它的候选。

## 三、top_k 敏感性：判定本身不稳定

为排除"候选截断压低结果"，用 `top_k=8` 与 `top_k=20` 各跑一次（同材料同 query）：

| 参数 | 覆盖 |
|---|---:|
| top_k=8 | 25/50 = 50% |
| top_k=20 | 23/50 = 46% |
| **并集** | **30/50 = 60%** |
| 交集 | 18/50 |

**候选变多反而略降**，且 **7 条从 covered/partial 翻成 missing** —— 同样的材料、同样的问题，
只因为候选列表变长。两轮**判定一致率仅 74%**。

抽查一条（「我怎么觉得注册指南和实际流程完全不一样」）：
- k8 候选含 `registration-process.txt` → 判 partial
- k20 该文件被挤出候选 → 判 missing，理由变成"属于渠道内部入驻口径"

**所以单次测量数不可靠。** 本报告同时给出高置信口径（两轮一致，34%）与并集口径（60%），
**决策应以 34% 为准**——因为不稳定的判定更可能是判错的（见第七节第 3 条）。

## 四、材料侧的事实

- 源站 `partnerplatform.bol.com`，**sitemap 有 752 个英文页**，实爬 **639 页 / 609 篇有正文 / 190 万字符**
- 第一轮只靠首页导航发现链接，只拿到 102 页 —— **发现页面必须先看 sitemap.xml**
- 该站静态 HTML 即含正文，不需要 JS 渲染，也不需要 firecrawl
- 文字密集、图片极少（VAT 那篇 6388 字符仅 2 张图），**不会踩 QA 阶段 `add_image_context=0` 的坑**

### 入驻漏斗：机制公开，专属实例不公开

- **非欧盟卖家没有独立的入驻内容页**：sitemap 里 `cdp/selling-via-bol*` 只有三个
  （入口 / `-as-nlbe-partner` / `-as-an-eu-partner`），猜测 slug 全部 404；
  入口页 "Are you based outside Europe?" 直接跳 `verkoper.bol.com/optiext/...` 申请表单
- **但入驻机制写在 EU partner 页里且可爬**：一次性邀请链接、5 个工作日无回复即未通过、
  明年可再申请、链接来自 bol 或 "selected integrator or agency"（即 Payoneer）
- **专属实例仍不可得**：注册链接是 `partner.bol.com/sdd/irvi/start/payoneer/<每人不同的 JWT>`

### 图片素材属于「爬不下来」而非「没有」

`ledp/checklist-starting-partner` 按钮写 "To the PDF"，实际是一张 **1189×1144 PNG**，
正文锁在图片里。读图转写后确认含真实入驻步骤（Create a bol account → 验证邮箱 →
两步验证 → Register your business → Set up sales account；EAN/GTIN/ISBN 检查）。
已转成文本并入语料。

⚠️ **但这类材料即使爬到也灌不进去**：本仓库挖掘流程 QA 生成阶段写死
`add_image_context=0`（`commons/schema_trans.py`），图片 OCR 结果不会进入喂给模型的正文。
要用图片材料必须先改挖掘方案。

## 七、给决策的建议

1. **Bol 达不到 80%（高置信 34% / 乐观上界 60%），且差距主要来自渠道内部口径，不是材料没爬够。** 继续加爬公开材料的边际收益已很低。
2. **优先修测量/检索侧，而不是继续灌材料。** 本试点里测量侧的修复贡献是材料侧的 3.5 倍
   （+28pp 切块 vs +8pp 材料翻 6 倍）。

   **量化版本**（payoneer-olive 汇总，本文复核过算式）：把「假缺口（候选截断）」和
   「默认分组挤占」两件事一起修，A 类覆盖率 **36.6% → 约 48%，一条新知识都不用灌**：

   | 项 | 条数 | 累计覆盖 |
   |---|---:|---:|
   | 基线 | 201/549 | 36.6% |
   | + 假缺口翻正（11.7% 全票口径，41 条） | 242 | 44.1% |
   | + 默认分组挤占翻正（**约 22 条**） | **264** | **≈48%** |

   > **2026-08-29 修正**：初版此处写 51.9%（按 43 条全部计入）。payoneer-olive 随后抽 20 条
   > 查了"目标知识在线上候选里排第几"，发现那 43 条是**两种失败混在一起**：
   > 排名 >12 的约一半是真被默认分组挤出候选（关默认分组有效）；
   > 排名 ≤12 的另一半**正确知识本来就在候选里、judge 仍判否**，属于精排侧，关默认分组解决不了。
   > 故只计入约一半，51.9% → 约 48%。**这也是"把推断当成验证结果"的又一个实例**：
   > 有"自有类目能答上"的数据，不等于"是被挤占的"，中间少了排名这一步。
3. **判定必须多次投票，且"不稳定"应当作质量信号**：两轮判定一致率仅 74%；
   payoneer-olive 实测**相同候选 + temperature=0 仍会飘**，且飘的条目与人工识别的误判高度重合。
   所以「跑 N 次看稳不稳」是一个**零成本的自动质检**，比人工抽查便宜——
   不稳定的判定优先当作"可能判错"处理，而不是取多数票了事。
4. **图片材料要先改挖掘方案**（`add_image_context=0`），否则爬到也灌不进去。
