# 聊天 QA 可复用知识挖掘 PRD v20260610.4

## 项目背景

knowledge_database_builder 用于从文档、网页、聊天记录等来源生成可检索知识，并转换为 ES schema 供搜索、审核和问答链路使用。聊天 QA 挖掘模块面向跨境电商运营群聊，不是全量复述聊天，而是从客户问题和运营/同事回答中沉淀未来可复用的业务知识。

当前核心问题有三类：

- 聊天上下文里说话人、身份和候选答案标记表达过重。例如 `客户｜客户/只能作为问题来源`、`运营同事｜同事/可作为答案来源[候选答案]` 会让模型和人工审核都看到重复标签。
- 文本 QA 链路过去只接收 `TEXT`，图片消息被直接跳过；如果上游把图片占位、图片路径或图片地址放在文本内容中，也可能被误当乱码或噪声丢弃。
- `should_enter_reuse_evaluation` 字段名过长，`qualification` 又不够直观。新版本统一使用 `is_qualified: true|false` 表示这条 QA 是否合格、是否值得作为可复用知识进入后续评估，不再兼容旧字段输入。
- 早期问题生成偏短，容易只形成“这个怎么处理”的标题式问题；新版本要求模型把与当前待评估答案直接相关的上下文背景整理进问题，提升后续搜索和人工复核可读性。

新版本需要保持“以当前待评估答案为中心”的抽取策略，同时把输入窗口表达改为更自然的 `客户xxx/问题来源`、`同事xxx/答案来源`、`本人xxx/当前待评估答案`，保留图片 supplement 供追溯，并支持多图片按 `图片1/图片2/图片3` 顺序标注。

## 业务概览

聊天 QA 挖掘链路由 `ChatQAMiningTaskController` 调度，按数据提取、QA 生成、质量分桶兼容、ES schema 转换、写 ES 的顺序执行。QA 生成阶段调用 `chatknowledge/gen_knowledge_from_chat.py`，从 MySQL 导出的聊天记录中按群配置和平台 prompt 构建候选窗口，再请求 LLM 输出结构化 JSON。

业务原则：

- 客户、未知身份、机器人、系统消息只能作为问题来源或上下文参考。
- leader/同事消息才允许作为答案来源。
- 生成逻辑以当前待评估答案为中心：拿当前待评估答案上方 50 句上下文倒推客户问题。
- 上下文不足、指代不清、当前待评估答案无法独立支撑答案时返回 `items: []`。
- 具体账号、店铺、订单、申请、工单、物流单状态查询默认不进入可复用知识。
- 产出的 QA 必须脱敏、泛化，不能包含真实人名、客户名、公司名、店铺名、账号、订单号、手机号、邮箱、微信号、链接等可定位个体的信息。
- 图片消息不能被当作乱码忽略。正文中以 `（图片N）` 呈现，多张图片按出现顺序递增编号，图片路径/地址等结构化信息进入 `supplement.images`。
- 问题文本需要尽量完整总结相关上下文：平台、业务阶段、当前动作、表单/资料/字段、前置条件、限制条件、异常现象、用户已尝试动作、截图指向的页面或按钮等；只允许使用聊天中实际出现且与当前待评估答案直接相关的信息。

## 核心数据字段

每条有效 QA 至少包含：

- `q`：补足业务背景且脱敏后的可搜索问题。
- `a`：只来自当前待评估答案、脱敏泛化后的答案。
- `quality_level`：`high | mid | low`。
- `is_qualified`：布尔值，表示该 QA 是否合格、是否值得进入后续可复用知识评估。
- `reuse_scope`：`general | platform_specific | case_specific`。
- `source_quote`：当前待评估答案中的关键原文，供追溯。
- `supplement`：可选补充信息，当前主要承载图片。格式示例：`{"images":[{"label":"图片1","address":"图片地址或路径"},{"label":"图片2","address":"图片地址或路径"}]}`。
- `from_chat_history`：本次抽取使用的上下文窗口，供人工复核。

`is_qualified` 是唯一有效字段。模型未返回该字段时 normalize 默认按 `false` 处理，ES schema 转换不再从 `qualification` 或 `should_enter_reuse_evaluation` 做兼容映射。

## 本版本需求

### 1. 聊天窗口可读化

把模型输入和 `from_chat_history` 中的聊天行从三段式改为两段式：

旧格式：

```text
10:00｜客户｜客户/只能作为问题来源：Wayfair 入驻时，营业执照经营范围没有覆盖这个类目，会影响提交吗？
10:03｜运营同事｜同事/可作为答案来源[候选答案]：需要先补充营业执照经营范围，再重新提交资料。
```

新格式：

```text
10:00｜客户/问题来源：Wayfair 入驻时，营业执照经营范围没有覆盖这个类目，会影响提交吗？
10:03｜运营同事/当前待评估答案：需要先补充营业执照经营范围，再重新提交资料。
```

规则：

- 客户消息显示为 `客户xxx/问题来源`，如果说话人本身就是“客户”，不重复成“客户客户”。
- 同事消息显示为 `同事xxx/答案来源`；如果说话人名已包含“同事”，不重复加前缀。
- leader/白名单消息显示为 `本人xxx/答案来源`。
- 当前候选 answer turn 内的 leader/同事消息显示为 `当前待评估答案`。
- 未识别消息显示为 `未识别xxx/上下文参考`，不能作为答案。

### 2. 多句候选答案合并

同一个 answer source 在 180 秒内连续发送的有效消息继续合并为一个 answer turn。示例：

```text
10:03｜运营同事/当前待评估答案：需要先补充营业执照经营范围，再重新提交资料。
10:04｜运营同事/当前待评估答案：提交前确认类目范围一致。
```

这两句应作为同一个候选答案窗口，模型可把它们共同作为当前待评估答案。

### 3. 图片与 supplement 处理

文本 QA 链路不能再简单跳过非 TEXT 消息：

- `ctype=IMAGE`、`IMG`、`PIC`、`PICTURE`、`PHOTO` 等图片消息进入聊天窗口。
- 主内容统一显示为 `（图片1）`、`（图片2）`、`（图片3）` 等，按群内窗口出现顺序递增编号。
- 图片地址、路径、下载状态等进入 `supplement.images`。
- 如果 `ctype=TEXT` 但内容是图片占位、图片 markdown、`<img>`、图片 URL 或本地图片路径，也按图片处理。
- 如果 `ctype=IMAGE_TEXT_MIX`、`MULTI_TYPE_MIX` 等图文混合消息中包含多张图片，正文保留文本并在对应位置追加多个图片占位，supplement 中保存多条图片记录。
- 图片 supplement 只用于人工追溯和上下文理解，不能单独作为可复用答案来源。

示例：

```text
10:01｜客户/问题来源：Wayfair 资料提交页面这个按钮一直是灰色的 （图片1） （图片2）

【supplement】
{"images":[{"label":"图片1","address":"https://example.com/a.png","type":"image"},{"label":"图片2","address":"https://example.com/b.png","type":"image"}]}
```

### 4. is_qualified 字段约束

Prompt 和 JSON 输出统一使用 `is_qualified`：

- `is_qualified=true`：信息完整、脱敏后仍通用、当前待评估答案能独立支撑答案，值得进入后续可复用知识评估。
- `is_qualified=false`：偏个案、上下文不足、低价值、需要人工大量补全、状态查询或催办类内容。
- 如果判断为 `is_qualified=false` 且没有保留价值，应直接输出 `{"items":[]}`。
- 旧字段 `qualification`、`should_enter_reuse_evaluation` 不再作为兼容输入，也不再作为新输出字段。

### 5. 问题上下文增强

模型生成 `q` 时不是简单概括客户最后一句话，而是要把相关上下文整理成后续可检索问题：

- 优先补足平台、入驻/审核/刊登/结算/物流等业务阶段。
- 补足当前动作，例如提交资料、填写表单、上传证件、绑定账号、点击按钮、查看审核状态。
- 补足表单、资料、字段、类目、按钮、页面、错误提示等对象。
- 补足用户已经说明的前置条件、限制条件或异常现象。
- 如果问题依赖图片，只能写“截图中该页面/按钮/提示”等聊天中可确认的信息，不能根据图片地址臆测视觉内容。
- 不把无关上下文或其他同事历史回答混入当前问题。

### 6. 过滤文案可理解

Prompt 中避免使用含混或拼写错误的过滤描述。图片占位、图片地址或可识别图片路径不要按“乱码”丢弃；不可读编码异常才作为噪声处理。预过滤、噪声过滤等内部概念不暴露为英文错拼或不可理解词。

### 7. 上下文不足误抽保护

如果模型已经在 `quality_reason` 中承认“上下文不足、指代不清、无法确定具体平台/场景、状态查询、催办、个案”等原因，同时 `is_qualified=false`，这类结果不是可保留的 low 样本，而是应该返回空的误抽。后处理需要直接预过滤掉，避免把“某个平台怎么填”这类伪知识写入后续链路。

## 验收标准

- 远端 `main` 已 fetch，确认没有落后远端再改动。
- `chatknowledge/gen_knowledge_from_chat.py` 语法检查通过。
- 示例 Wayfair 入驻资料问题生成的 prompt 中不再出现 `客户｜客户/只能作为问题来源` 或 `[候选答案]`。
- 示例中同一运营同事 180 秒内连续两句仍合并为一个 answer turn。
- 个案状态查询样例仍可被规则约束为不应抽取可复用 QA。
- 上下文不足样例即使模型返回 `low + is_qualified=false`，后处理也应预过滤为空。
- 图片消息不会被 `ctype != TEXT` 跳过；prompt 中能看到 `（图片N）`，QA 输出或 ES `ext_info` 中能看到 `supplement.images`。
- 多图图文混合消息能在正文中看到 `（图片1） （图片2）` 等多个占位，supplement 中保留多条图片地址。
- `is_qualified` 字段在 normalize 和 ES `ext_info` 中保留；旧 `qualification`、`should_enter_reuse_evaluation` 不再兼容映射。
- 真实抽样需要使用生产聊天窗口和真实模型输出，不用合成样本替代；抽样结果需包含 turn、system prompt、user prompt、raw output、normalized output，供人工 review。

## 历史概述

- 早期版本从聊天全窗口抽取 QA，容易把客户、同事、leader 的多段内容混在一起。
- 后续改为“以 leader/同事候选答案为中心”：只把候选答案作为答案来源，上方 50 句上下文仅用于倒推问题。
- 2026-06-10 之前新增 `should_enter_reuse_evaluation`，区分“抽到了 QA”和“是否值得进入可复用知识评估”。
- 本版本继续沿用候选答案中心策略，只优化模型输入和复核历史的角色表达，减少“说话人 + 身份”重复导致的理解干扰。
- 2026-06-10.2 将 `should_enter_reuse_evaluation` 简化为 `qualification`，并把图片消息从“跳过/疑似乱码”调整为“正文图片占位 + supplement 追溯”的结构化处理。
- 2026-06-10.3 将字段进一步调整为更符合模型理解的 `is_qualified`，历史 `qualification` 和 `should_enter_reuse_evaluation` 仅做兼容输入；同时加强问题生成规则，要求把相关上下文背景尽量整理进 q，并验证多图片编号和 supplement 保留。
- 2026-06-10.4 去掉旧字段兼容逻辑，只认 `is_qualified`；同时增加真实聊天窗口十轮随机抽样要求，用真实模型结果供人工评估。

## 非目标

- 不修改 ES 写入定时任务。
- 不改 MySQL 数据提取范围。
- 不改图片本身的 OCR 或视觉理解能力；本版本只保证图片消息不丢、地址可追溯。
- 不引入前端页面或人工审核 UI 改造。
