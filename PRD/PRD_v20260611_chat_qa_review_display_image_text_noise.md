# 聊天 QA 可复用知识挖掘 PRD v20260611.2

## 项目背景

knowledge_database_builder 用于从文档、网页、聊天记录等来源生成可检索知识，并转换为 ES schema 供搜索、审核和问答链路使用。聊天 QA 挖掘模块面向跨境电商运营群聊，不是全量复述聊天，而是从客户问题和运营/同事回答中沉淀未来可复用的业务知识。

当前核心问题有三类：

- 聊天上下文里说话人、身份和候选答案标记表达过重。例如 `客户｜客户/只能作为问题来源`、`运营同事｜同事/可作为答案来源[候选答案]` 会让模型和人工审核都看到重复标签。
- 文本 QA 链路过去只接收 `TEXT`，图片消息被直接跳过；如果上游把图片占位、图片路径或图片地址放在文本内容中，也可能被误当乱码或噪声丢弃。
- `should_enter_reuse_evaluation` 字段名过长，`qualification` 又不够直观。新版本统一使用 `is_qualified: true|false` 表示这条 QA 是否合格、是否值得作为可复用知识进入后续评估，不再兼容旧字段输入。
- 早期问题生成偏短，容易只形成“这个怎么处理”的标题式问题；新版本要求模型把与当前待评估答案直接相关的上下文背景整理进问题，提升后续搜索和人工复核可读性。
- 真实抽样发现 `[群聊信息已更新]`、入群欢迎/群规则公告、营销广告和福利宣传会进入候选窗口，影响模型判断。新版本增加噪声过滤，避免这些内容进入上下文和当前待评估答案。
- 进一步 5 轮、每轮 1000 条真实消息抽样发现，残留噪声主要包括引用回复包装、群管理尾巴、纯链接/教程合集、个案协作、索要手机号/邮箱、英文短确认和明显离题闲聊。新版本同时增加规则过滤和 prompt 过滤。
- 纯图片也可能是同事给出的答案，例如操作截图、路径截图、模板截图。新版本不再在候选阶段过滤纯图片答案，但要求模型不能脑补图片内容；图片型答案的真实载体是系统后台图片地址/路径，而不是 `图片N` 文本占位。
- 真实抽样 review 发现 user prompt 中混入了大量固定规则、metadata 和“from_chat_history 参数”，导致 turn 构建不够干净，也不利于模型缓存。新版本将工作目标、业务背景、拼接方式、噪声排除、分类标准、图片处理和输出 schema 全部放入固定 system prompt；user prompt 只保留动态对话窗口。
- 真实抽样还发现部分 q/a 会过度扩写，a 从上方上下文里补充了当前待评估答案没有说的内容。新版本强调 q/a 都要忠于原文：q 只能整理真实相关上下文，a 只能来自当前 answer turn，短答案保持短答案，不为“看起来完整”而脑补。
- 图片后台路径不能只保存 `/root/dify/dify-on-wechat/tmp/...` 或 `tmp/...`，也不能硬拼未上传的 `file.marsmind.cc/tmp/...`。新版本在后台文件存在时上传到 MinIO 多模态 bucket，以 hash 对象路径生成可公网访问的 file service URL，并在 supplement 中保留 `backend_url/public_url/minio_bucket/minio_object_key/minio_path/backend_file_path/backend_path`。
- 人工 review 抽样文件中，当前待评估答案不需要再以多行 `Turn` 块强调内部概念；应合并为单行“当前待评估答案（合并）”，真实送模型的 `User Prompt` 保持原文完整展示。
- 进一步检查真实样本发现，图文混合消息如果文本部分只是引用回复包装、@尾巴或不可读编码，但图片 supplement 有效，过去会因为“有图片”而保留脏文本。新版本应保留图片载体，但把无业务意义的文本替换为图片占位；如果文本是广告、群公告、活动报名、个案协作等明确噪声，则整条过滤。

新版本需要保持“以当前待评估答案为中心”的抽取策略，同时把输入窗口表达改为更自然的 `客户xxx/问题来源`、`同事xxx/答案来源`、`本人xxx/当前待评估答案`，保留图片 supplement 供追溯，并支持多图片按 `图片1/图片2/图片3` 顺序标注。

## 业务概览

聊天 QA 挖掘链路由 `ChatQAMiningTaskController` 调度，按数据提取、QA 生成、质量分桶兼容、ES schema 转换、写 ES 的顺序执行。QA 生成阶段调用 `chatknowledge/gen_knowledge_from_chat.py`，从 MySQL 导出的聊天记录中按群配置和平台 prompt 构建候选窗口，再请求 LLM 输出结构化 JSON。

业务原则：

- 客户、未知身份、机器人、系统消息只能作为问题来源或上下文参考。
- leader/同事消息才允许作为答案来源。
- 生成逻辑以当前待评估答案为中心：拿当前待评估答案上方 50 句上下文倒推客户问题。
- 上下文不足、指代不清、当前待评估答案无法独立支撑答案时返回 `items: []`。
- 具体账号、店铺、订单、申请、工单、物流单状态查询默认不进入可复用知识。
- 产出的 QA 必须脱敏、泛化，不能包含真实人名、客户名、公司名、店铺名、账号、订单号、手机号、邮箱、微信号、链接等可定位个体的信息。
- 图片消息不能被当作乱码忽略。正文中以 `（图片N）` 呈现，多张图片按出现顺序递增编号，图片路径/地址等结构化信息进入 `supplement.images`。
- 问题文本需要尽量完整总结相关上下文：平台、业务阶段、当前动作、表单/资料/字段、前置条件、限制条件、异常现象、用户已尝试动作、截图指向的页面或按钮等；只允许使用聊天中实际出现且与当前待评估答案直接相关的信息。
- 群系统噪声、群公告/欢迎规则、营销广告、福利宣传、活动海报等内容默认不进入 QA 抽取窗口。
- 中英文短确认如 `yes/no/sure/thanks` 与 `好/收到/可以` 一样，不能作为当前待评估答案。
- 英文寒暄/等待/误解类短句如 `noted`、`one moment`、`wait a moment`、`sorry, I misunderstood` 不能作为当前待评估答案。
- 纯图片消息可以作为问题上下文，也可以作为同事/leader 的答案候选；如果最终抽取 QA，必须保留 `supplement.images`。
- 图片型答案不要求最终 `a` 显式引用 `图片N`。`图片N` 只是模型输入里的占位符，真正可追溯答案是 `supplement.images` 中的 `backend_url`、`backend_path`、`backend_file_path` 或原始 `address`。
- 图片型答案优先使用可公网访问的 `backend_url/public_url`；如果本地后台文件存在，应上传 MinIO 后生成 file service URL。只有上传失败或文件不存在时，才保留 `backend_file_path/backend_path/address` 作为兜底追溯字段。
- 如果当前 answer turn 是纯图片，没有同 turn 文本口径，后处理应把最终 `a` 规整为图片后台 URL/路径本身，不能写成“参考图片N”，也不能把上方上下文里的同事文字答案拼进来。
- 最终 QA 不能无差别合并上方 50 句上下文里的所有图片；程序只自动合并当前待评估答案 turn 的图片。上下文图片只作为模型输入，除非模型在输出 supplement 中明确回传为相关图片。
- 引用回复包装中的被引用原文、长分隔线和群管理尾巴应在装配前清理，尽量只保留同事真正回复的业务口径。
- `from_chat_history` 应保存干净的动态对话窗口，不保存 system prompt、规则说明或 metadata 参数，方便人工 review 直接看原始上下文。
- 如果模型已经判断 `is_qualified=false`，且原因明确是“答案过于简短、缺乏具体步骤、无法独立复用、复用价值低”等低价值误抽，应在后处理中过滤为空，不进入最终 QA。

## 核心数据字段

每条有效 QA 至少包含：

- `q`：补足业务背景且脱敏后的可搜索问题。
- `a`：只来自当前待评估答案、脱敏泛化后的答案；纯图片答案时为图片后台 URL/路径本身。
- `quality_level`：`high | mid | low`。
- `is_qualified`：布尔值，表示该 QA 是否合格、是否值得进入后续可复用知识评估。
- `reuse_scope`：`general | platform_specific | case_specific`。
- `source_quote`：当前待评估答案中的关键原文，供追溯。
- `supplement`：可选补充信息，当前主要承载图片。格式示例：`{"images":[{"label":"图片1","backend_url":"图片后台URL","backend_path":"图片后台路径","backend_file_path":"后台文件路径","address":"原始图片地址或路径"}]}`。
- `from_chat_history`：本次抽取使用的干净上下文窗口，供人工复核；不能包含固定 prompt 规则、metadata 参数或模型输出说明。

`is_qualified` 是唯一有效字段。模型未返回该字段时 normalize 默认按 `false` 处理，ES schema 转换不再从 `qualification` 或 `should_enter_reuse_evaluation` 做兼容映射。

## 本版本需求

### 1. 聊天窗口可读化

把模型输入和 `from_chat_history` 中的聊天行从三段式改为两段式：

旧格式：

```text
10:00｜客户｜客户/只能作为问题来源：Wayfair 入驻时，营业执照经营范围没有覆盖这个类目，会影响提交吗？
10:03｜运营同事｜同事/可作为答案来源[候选答案]：需要先补充营业执照经营范围，再重新提交资料。
```

新格式：

```text
10:00｜客户/问题来源：Wayfair 入驻时，营业执照经营范围没有覆盖这个类目，会影响提交吗？
10:03｜运营同事/当前待评估答案：需要先补充营业执照经营范围，再重新提交资料。
```

规则：

- 客户消息显示为 `客户xxx/问题来源`，如果说话人本身就是“客户”，不重复成“客户客户”。
- 同事消息显示为 `同事xxx/答案来源`；如果说话人名已包含“同事”，不重复加前缀。
- leader/白名单消息显示为 `本人xxx/答案来源`。
- 当前候选 answer turn 内的 leader/同事消息显示为 `当前待评估答案`。
- 未识别消息显示为 `未识别xxx/上下文参考`，不能作为答案。

### 2. 多句候选答案合并

同一个 answer source 在 180 秒内连续发送的有效消息继续合并为一个 answer turn。示例：

```text
10:03｜运营同事/当前待评估答案：需要先补充营业执照经营范围，再重新提交资料。
10:04｜运营同事/当前待评估答案：提交前确认类目范围一致。
```

这两句应作为同一个候选答案窗口，模型可把它们共同作为当前待评估答案。

### 3. 图片与 supplement 处理

文本 QA 链路不能再简单跳过非 TEXT 消息：

- `ctype=IMAGE`、`IMG`、`PIC`、`PICTURE`、`PHOTO` 等图片消息进入聊天窗口。
- 主内容统一显示为 `（图片1）`、`（图片2）`、`（图片3）` 等，按群内窗口出现顺序递增编号。
- 图片地址、路径、下载状态等进入 `supplement.images`；如果原始数据有 http/s3/oss/cos/minio 地址，写入 `backend_url`；如果只有 `tmp/...` 这类后台相对路径，写入 `backend_path` 和按业务后台根目录补齐的 `backend_file_path`。
- 如果 `ctype=TEXT` 但内容是图片占位、图片 markdown、`<img>`、图片 URL 或本地图片路径，也按图片处理。
- 如果 `ctype=IMAGE_TEXT_MIX`、`MULTI_TYPE_MIX` 等图文混合消息中包含多张图片，正文保留文本并在对应位置追加多个图片占位，supplement 中保存多条图片记录。
- 图片 supplement 是图片型答案的真实载体。纯图片答案可以只通过 `supplement.images` 承载答案，最终 `a` 由后处理规整为图片后台 URL/路径。

示例：

```text
10:01｜客户/问题来源：Wayfair 资料提交页面这个按钮一直是灰色的 （图片1） （图片2）

【supplement】
{"images":[{"label":"图片1","backend_url":"https://example.com/a.png","address":"https://example.com/a.png","type":"image"},{"label":"图片2","backend_url":"https://example.com/b.png","address":"https://example.com/b.png","type":"image"}]}
```

### 4. is_qualified 字段约束

Prompt 和 JSON 输出统一使用 `is_qualified`：

- `is_qualified=true`：信息完整、脱敏后仍通用、当前待评估答案能独立支撑答案，值得进入后续可复用知识评估。
- `is_qualified=false`：偏个案、上下文不足、低价值、需要人工大量补全、状态查询或催办类内容。
- 如果判断为 `is_qualified=false` 且没有保留价值，应直接输出 `{"items":[]}`。
- 旧字段 `qualification`、`should_enter_reuse_evaluation` 不再作为兼容输入，也不再作为新输出字段。

### 5. 问题上下文增强

模型生成 `q` 时不是简单概括客户最后一句话，而是要把相关上下文整理成后续可检索问题：

- 优先补足平台、入驻/审核/刊登/结算/物流等业务阶段。
- 补足当前动作，例如提交资料、填写表单、上传证件、绑定账号、点击按钮、查看审核状态。
- 补足表单、资料、字段、类目、按钮、页面、错误提示等对象。
- 补足用户已经说明的前置条件、限制条件或异常现象。
- 如果问题依赖图片，只能写“截图中该页面/按钮/提示”等聊天中可确认的信息，不能根据图片地址臆测视觉内容。
- 不把无关上下文或其他同事历史回答混入当前问题。

### 6. 过滤文案可理解

Prompt 中避免使用含混或拼写错误的过滤描述。图片占位、图片地址或可识别图片路径不要按“乱码”丢弃；不可读编码异常才作为噪声处理。预过滤、噪声过滤等内部概念不暴露为英文错拼或不可理解词。

### 7. 噪声和广告过滤

真实聊天整理阶段需要过滤以下内容：

- 群系统提示：`[群聊信息已更新]`、群公告/群名称更新等。
- 入群噪声：扫码入群、邀请入群、欢迎加入、群规则、群昵称修改提醒、群公告提示、定期清退等。
- 明显营销广告：扫码报名、报名链接、限时福利、新人福利、服务商礼包、招商大会、闭门私董会、直播/课程报名、训练营直播课堂、开播提醒、峰会海报等。
- 短确认和寒暄：`yes/no/sure/thanks`、`好/收到/可以/谢谢` 等不能成为候选答案。
- 信息收集反问：同事追问客户手机号、邮箱、截图、月流水、账号等信息时不作为答案来源。
- 纯图片答案：同事只发 `（图片N）` 且没有文字口径时可以作为候选答案；模型必须回传当前图片的 `supplement.images`，最终答案由程序规整为图片后台 URL/路径，不能臆测图片细节。
- 引用包装：企业微信/微信回复格式中出现的被引用原文、长分隔线、重复问题不作为答案来源；如果尾部有真实业务回复，只保留回复尾部。
- 纯资源转发：只有链接、教程合集、资料合集、官网学习链接且没有具体业务口径的消息不进入候选答案。
- 个案协作：帮忙申诉、催办、已反馈、我看看、索要手机号/邮箱/截图以便处理等临时协作不进入候选答案。
- 明显离题闲聊：食物、课程作业、非业务资源闲聊等不进入上下文。
- 广告过滤要避免误杀真实业务问题，例如“广告功能怎么开”“活动报名入口不显示”这类带问号或排障语义的客户问题不能按广告丢弃。

### 8. 上下文不足误抽保护

如果模型已经在 `quality_reason` 中承认“上下文不足、指代不清、无法确定具体平台/场景、状态查询、催办、个案”等原因，同时 `is_qualified=false`，这类结果不是可保留的 low 样本，而是应该返回空的误抽。后处理需要直接预过滤掉，避免把“某个平台怎么填”这类伪知识写入后续链路。

### 9. 固定 system prompt 与干净 user prompt

LLM 请求必须拆为固定 system prompt 和动态 user prompt：

- system prompt 固定，便于模型端缓存。
- system prompt 内包含：工作目标、业务背景、输入格式、拼接方式、答案来源约束、QA 抽取类型、噪声排除、q/a 忠实度要求、图片处理、质量分级、is_qualified 规则、输出 JSON schema。
- user prompt 只放本次动态对话窗口：
  - `【上方50句上下文】`
  - 干净聊天行
  - `【当前待评估答案】`
  - 当前 answer turn 聊天行
  - 可选 `【supplement】`
- user prompt 不再包含 metadata、群名、客户平台参数、规则说明、示例、分类标准或“不要写入 q/a”等固定文案。
- `from_chat_history` 与 user prompt 一致，作为人工复核的干净对话窗口。

### 10. q/a 忠于原文

- q 可以整合上下文背景，但只能使用聊天里真实出现、且与当前待评估答案直接相关的信息。
- q 不得把上方其他同事历史回答拼成当前问题背景。
- a 尽量保留当前待评估答案原文，只允许去掉称呼、个人信息、口头语和明显引用包装。
- a 默认保持当前待评估答案的原始语言和核心措辞，不把英文答案翻译成中文，也不把中文答案翻译成英文。
- a 不得补充当前待评估答案未表达的条件、步骤、原因、承诺或链接。
- 当前待评估答案很短但确实是规则时，a 保持短答案；不要为了完整性从上下文补口径。
- 图片 URL/路径型答案不能被数字脱敏破坏。

### 11. 图片公网 URL 生成

当图片 supplement 只有后台路径时，处理顺序如下：

1. 规整 `backend_path` 和 `backend_file_path`，默认后台根路径为 `/root/dify/dify-on-wechat`。
2. 如果 `backend_file_path` 对应文件存在，上传到 MinIO 多模态 bucket。
3. 对象路径使用 hash 方式生成，避免暴露原始 `tmp/...` 业务路径。
4. 如果配置了 `prefix_fileservice_url` 和 bucket，生成 `https://file.marsmind.cc/{bucket}/{object_key}` 形式的公网 URL。
5. supplement 中写入 `backend_url`、`public_url`、`minio_bucket`、`minio_object_key`、`minio_path`，同时保留 `backend_file_path`、`backend_path`、`address`。
6. 如果上传失败或文件不存在，不硬拼不可访问 URL，只保留后台路径兜底。

### 12. 抽样 review 展示与图文混合噪声兜底

人工 review 文件需要更贴近审核动作：

- 不再输出 `### Turn` 标题。
- 当前待评估答案合并为单行 `### 当前待评估答案（合并）`，多句之间用 ` / ` 串联，便于快速扫读。
- `User Prompt` 必须继续保留完整原文，因为它才是真实送模型的动态输入。
- JSON 结果仍保留 `turn` 字段，供机器处理和后续排查。
- Markdown 默认不展示 `Existing Task Result Samples`，因为它是历史任务样例，不是本轮模型输入输出，容易把旧格式和旧噪声混入人工 review。

图文混合消息需要区分“图片有效、文本无效”和“整条消息是噪声”：

- 文本只是引用包装、被引用原文尾巴、单纯 @ 人、不可读编码时，删除文本，仅保留 `（图片N）` 占位和 supplement 图片信息。
- 引用包装分隔符可能是 `/ ------ /`，也可能是换行版 `------\n@xxx`；清理时取最后一个长分隔符后的真实回复尾部。
- 文本包含真实业务口径时，保留业务文本和图片占位。
- 如果同一句里前半段是业务规则、后半段是邀请返奖/活动链接/更多奖品推广，只保留业务规则，删除推广尾巴。
- 文本命中广告营销、群公告/群规则、活动报名、资源推广、个案协作、离题闲聊等噪声时，即使带图片 supplement，也整条过滤。
- 这层兜底只影响进入模型的聊天窗口干净度，不改变“纯图片可以作为答案”的原则。

## 验收标准

- 远端 `main` 已 fetch，确认没有落后远端再改动。
- `chatknowledge/gen_knowledge_from_chat.py` 语法检查通过。
- 示例 Wayfair 入驻资料问题生成的 prompt 中不再出现 `客户｜客户/只能作为问题来源` 或 `[候选答案]`。
- 示例中同一运营同事 180 秒内连续两句仍合并为一个 answer turn。
- 个案状态查询样例仍可被规则约束为不应抽取可复用 QA。
- 上下文不足样例即使模型返回 `low + is_qualified=false`，后处理也应预过滤为空。
- 低价值误抽样例，例如 `check this to register`、无链接的“看这里”、缺少具体步骤的短句，即使模型返回了 JSON item，也应被后处理过滤为空。
- 图片消息不会被 `ctype != TEXT` 跳过；prompt 中能看到 `（图片N）`，QA 输出或 ES `ext_info` 中能看到 `supplement.images`。
- 多图图文混合消息能在正文中看到 `（图片1） （图片2）` 等多个占位，supplement 中保留多条图片地址。
- `is_qualified` 字段在 normalize 和 ES `ext_info` 中保留；旧 `qualification`、`should_enter_reuse_evaluation` 不再兼容映射。
- 真实抽样需要使用生产聊天窗口和真实模型输出，不用合成样本替代；抽样结果需包含 turn、system prompt、user prompt、raw output、normalized output，供人工 review。
- 十轮真实抽样中不应再出现 `[群聊信息已更新]`、入群欢迎/群规则公告或明显广告福利宣传作为当前待评估答案。
- 十轮真实抽样中不应再出现 `yes/no/sure/thanks` 这类短确认作为可保留 QA。
- 十轮真实抽样中纯图片可以作为候选答案；最终 QA 的纯图片答案应体现为图片后台 URL/路径，而不是“参考图片N”；英文等待/道歉寒暄、同事反问客户信息仍不应作为候选答案。
- system prompt 在同一版本内固定不随群和客户变化；user prompt 只包含动态对话窗口和 supplement。
- `from_chat_history` 不再包含 metadata 和规则说明，应能直接作为“干净 turn 构建”给人工 review。
- 图片文件存在时，supplement 中应看到可公网访问的 `backend_url/public_url` 和 MinIO 对象信息；图片地址型 `a` 不应被数字脱敏。
- 抽样 Markdown 中不再出现 `### Turn`，当前待评估答案应以单行合并展示。
- 图文混合消息中的引用包装、@尾巴或不可读文本不应再污染 `【当前待评估答案】`；若有图片 supplement，应显示为对应 `（图片N）`。
- 带图片的广告/群公告/活动报名等噪声不应因为存在 supplement 而进入上下文或候选答案。
- 5 轮、每轮 1000 条真实消息抽样需产出噪声类别统计和样例，用于确认规则覆盖面。
- Prompt 中必须明确要求模型忽略残留引用包装、群管理、广告营销、链接合集、个案协作和短确认。

## 历史概述

- 早期版本从聊天全窗口抽取 QA，容易把客户、同事、leader 的多段内容混在一起。
- 后续改为“以 leader/同事候选答案为中心”：只把候选答案作为答案来源，上方 50 句上下文仅用于倒推问题。
- 2026-06-10 之前新增 `should_enter_reuse_evaluation`，区分“抽到了 QA”和“是否值得进入可复用知识评估”。
- 本版本继续沿用候选答案中心策略，只优化模型输入和复核历史的角色表达，减少“说话人 + 身份”重复导致的理解干扰。
- 2026-06-10.2 将 `should_enter_reuse_evaluation` 简化为 `qualification`，并把图片消息从“跳过/疑似乱码”调整为“正文图片占位 + supplement 追溯”的结构化处理。
- 2026-06-10.3 将字段进一步调整为更符合模型理解的 `is_qualified`，历史 `qualification` 和 `should_enter_reuse_evaluation` 仅做兼容输入；同时加强问题生成规则，要求把相关上下文背景尽量整理进 q，并验证多图片编号和 supplement 保留。
- 2026-06-10.4 去掉旧字段兼容逻辑，只认 `is_qualified`；同时增加真实聊天窗口十轮随机抽样要求，用真实模型结果供人工评估。
- 2026-06-10.5 增加群系统噪声、入群公告和广告营销过滤；用户已明确批准将真实抽样窗口发送到当前配置模型端点进行十轮真实输出验证。
- 2026-06-10.6 基于 5x1000 真实消息抽样，新增引用回复清洗、群管理尾巴清理、资源链接、个案协作、明显离题闲聊和 prompt 噪声约束。
- 2026-06-10.7 恢复纯图片作为答案候选的能力，并放宽图片型答案的后处理重叠校验；真实抽样 review 需要展示 system prompt、进入模型的 turn/user prompt、raw output 和最终 QA。
- 2026-06-10.8 修正图片答案口径：`图片N` 只是占位符，不是最终答案；纯图片答案必须以系统后台图片 URL/路径作为 `a`，并保留 `supplement.images` 用于人工复核和后续链路。
- 2026-06-10.8 补充限制最终 QA 的 supplement 合并范围：不再自动把整段上下文的所有图片写进 QA，只自动补当前待评估答案 turn 的图片，避免无关图片污染审核结果。
- 2026-06-11.1 将固定抽取规则从 user prompt 移入 system prompt，user prompt/from_chat_history 只保留干净动态对话窗口；加强 q/a 忠于原文要求；图片后台文件存在时上传 MinIO 并生成可公网访问的 file service URL，图片 URL/路径答案不再被数字脱敏破坏。
- 2026-06-11.1 基于 30 条真实随机抽样，新增 `is_qualified=false` 低价值误抽过滤：对“答案过于简短、缺乏具体步骤、无法独立复用、复用价值低”等模型自认低价值结果直接丢弃。
- 2026-06-11.2 根据人工 review 反馈，将抽样 Markdown 中的多行 `Turn` 改为单行“当前待评估答案（合并）”；Markdown 去掉历史任务样例区块；补齐换行版引用包装清理；对图文混合消息增加“保留图片、丢弃无意义文本；广告/公告类整条过滤”的兜底；对“业务规则 + 邀请返奖/活动链接”消息删除推广尾巴。
